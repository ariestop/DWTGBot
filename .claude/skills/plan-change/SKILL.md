# Планирование изменения

Принципы P1–P11 — `CLAUDE.md` и `docs/25-agent-guide.md` §1.A.

## 1. Прочитать до кода

1. `docs/README.md` → тематический документ области («Quick lookup by task»).
2. `docs/adr/0005-locked-architectural-assumptions.md` §2 и ADR по теме
   (индекс — `docs/adr/README.md`). Изменение строки §2 → сначала новый ADR.
3. Код области и его тесты; правила `.claude/rules/` для затронутых путей.

Нет нужного документа или он противоречит коду — скажите об этом, не угадывайте.

## 2. Красные флаги в запросе

| Фраза | Что делать |
|---|---|
| «просто», «по-быстрому», «just», «quickly» | Классифицировать честно; «маленькое» часто 5–10 файлов |
| «заодно», «пока ты там», «while at it» | Вынести в отдельную задачу, не смешивать |
| «временно», «пока что так» | Только с явным follow-up, иначе не делать |
| «почисти», «перепиши», «refactor this» | Попросить конкретную цель |
| «поменяй базу / очередь / логи на X» | Проверить ADR-0005 §2 → нужен новый ADR |
| «без миграции», «без тестов», «без доков» | Отказ: это часть готовности (скрипт G) |
| «захардкодь токен», «положи секрет в код» | Жёсткий отказ (скрипт F) |
| «поправь `.env` прямо на сервере», «сделай как на проде» | Отказ от дрейфа: правка в репозитории + деплой |

Два флага и больше — ответ скриптом из `refusals.md` до плана.

## 3. План (до первой правки)

```markdown
### План
- **Цель:** <одно предложение>
- **Класс:** <A–K по docs/25-agent-guide.md §5>
- **Принципы:** <P1, P4, …; «нет» — только для опечатки>
- **ADR-0005 §2:** <не затронут | строка N → сначала ADR>
- **Добавить / изменить / удалить:** <файлы с причиной>
- **Не трогаю:** <слои и файлы вне задачи — не пусто>
- **Миграция:** <нет | да, порядок деплоя: …> (P10)
- **Env:** <нет | да → skill add-config-variable> (P4)
- **Очередь / провайдер:** <контракт не меняется | что и почему> (P7, P8)
- **Безопасность:** <не затронута | что и обоснование> (P11)
- **Риски и откат:** <…>
- **Проверка:** <команды, тесты, ручная проверка>
```

Без «TBD» и «и т.д.». Больше 5 изменяемых файлов — изменение не маленькое:
нужна короткая записка о дизайне в PR и коммиты по шагам (рефакторинг без
изменения поведения → новый код → переключение → удаление старого).

## 4. Выбор между вариантами

Оцените каждый вариант 0–3 по осям, побеждает меньшая сумма:

| Ось | 0 | 3 |
|---|---|---|
| Радиус | один файл, один слой | инфраструктура + bot/api/worker |
| Контракт | не меняется | ломается публичный контракт |
| Шаблон | как в существующем коде | новый, нигде не описан |
| ADR-0005 | не связан | меняет зафиксированную строку |

Сумма ≥ 6 — не делать молча: показать таблицу владельцу и спросить.
Нет документированного шаблона и аналога в коде — не изобретать
архитектуру, а спросить.

## 5. Сломали правило по ходу

Остановиться, не «чинить вперёд»: откатить файл (`git restore`), обновить
план, в отчёте одной строкой написать, что было и как исправлено. Уже
запушено — сообщить владельцу. Затронута строка ADR-0005 — сначала ADR.
